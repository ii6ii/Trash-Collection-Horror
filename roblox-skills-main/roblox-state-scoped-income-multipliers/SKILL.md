# Условные мультипликаторы дохода Roblox

Применяй бонус к каждой авторитетно классифицированной income-contribution, а не к общему доходу игрока. Если бонус работает лишь для части источников, не регистрируй его как безусловный глобальный provider.

## Зафиксируй контракт

Перед кодом или ревью:

1. Найди точную формулировку ТЗ, config бонуса и текущий pipeline мультипликаторов.
2. Составь матрицу всех cash sinks: live idle объекты по состояниям, offline income, Hit Cash, Steal и другие пути начисления. Для каждого укажи `apply`, `exclude` или `needs decision` со ссылкой на ТЗ.
3. Найди авторитетный predicate целевого состояния: state, owner, активную базу и нужную hierarchy. Не доверяй одному имени модели, клиентскому флагу или только `Parent`.
4. Определи, что хранит offline pipeline: чистую base rate или уже умноженную rate. Не применяй бонус дважды.

Формулировка «весь idle-доход базы» по умолчанию включает offline income. Если отдельный offline service не использует нужный бонус, не выдавай это за намеренное исключение: получи явное product-решение. Hit Cash и Steal включай только если ТЗ связывает их с тем же cash multiplier.

## Классифицируй contribution на сервере

Вычисляй eligibility рядом с авторитетной моделью домена и передавай её в income snapshot вместе с rate. Один и тот же predicate должен определять как участие в доходе, так и применимость scoped-бонуса.

Для контракта Parked SCP обычно недостаточно только `state == "World"`: проверь, что объект принадлежит игроку и является descendant папки блоков его текущей базы. Carried contribution должна сохранять отдельную классификацию, даже если она входит в общий live income.

Если fallback API возвращает лишь общую rate без contributions, не применяй scoped-бонус ко всей сумме. Либо получи детализированный snapshot, либо оставь путь без бонуса и зафиксируй ограничение.

## Скомбинируй без второй базовой единицы

Сначала определи Mode по текущей кодовой базе. Для ADD-комбинирования, где каждый multiplier уже содержит базовую `1`, используй:

```text
effectiveMultiplier = existingMultiplier + (scopedMultiplier - 1)
```

Не складывай полные multipliers: это добавит вторую базовую единицу. Не заменяй ADD на MULT без изменения контракта. Сохрани существующий порядок block-specific bonuses, aggregate cash multiplier, clamps и внешних модификаторов, если ТЗ не меняет его явно.

Контрольный пример:

```text
existingMultiplier = 4
scopedMultiplier = 1 + 175 / 100 = 2.75
Parked: 10 * (4 + 2.75 - 1) = 57.5
Carried: 10 * 4 = 40
Total: 97.5
```

## Проверка

Добавь focused tests на изменённый контракт:

- целевая contribution получает scoped-бонус, нецелевая получает только общие modifiers;
- пограничные states, stale/foreign objects и объект в чужой hierarchy не получают бонус;
- смешанный snapshot с целевой и нецелевой contributions даёт точный общий доход и те же суммы в per-object feedback;
- `scopedMultiplier == 1` ничего не меняет, а невалидные значения обрабатываются по текущей политике сервиса;
- offline income покрыт тестом на применение бонуса или явно зафиксированное исключение;
- Hit Cash, Steal и другие sinks остаются без бонуса, когда их исключает контракт;
- публичные income totals, payout и UI/analytics не расходятся из-за двух разных формул.

На ревью покажи матрицу sinks, predicate, Mode, ручной числовой пример и тесты. Расхождение между формулировкой «весь idle-доход» и непокрытым offline pipeline выноси отдельно и не закрывай до явного решения.

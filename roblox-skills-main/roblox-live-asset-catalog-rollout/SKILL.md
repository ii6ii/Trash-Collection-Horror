# Каталожный rollout live-ассетов Roblox

Используй этот workflow, когда каталог определяет доступные шаблоны, профиль хранит права и выбранный вариант, а внешний вид нужно применить к уже работающим Roblox-инстансам без потери их identity.

Если задача меняет стабильные ID, порядок или состав существующего каталога, также прочитай [roblox-data-catalog-migration](../roblox-data-catalog-migration/SKILL.md).

## 1. Зафиксируй контракт до правок

Прочитай каталог, схему профиля, `Reconcile`, место сохранения, все точки применения ассета и связанные тесты. Если реальная Studio-иерархия не представлена файлами, проверь её read-only через доступный Studio-инструмент или запроси точную структуру.

Для каждой категории запиши:

- стабильный ID записи и путь к template;
- исторический источник прав игрока;
- сохранённые поля ownership/equipped/version;
- корневой live-Instance, identity которого нельзя менять;
- его attributes, connections и внешние ссылки, которые должны сохраниться;
- заменяемых и опциональных детей;
- anchor для относительного transform;
- свойства, копируемые из template в существующие live-объекты.

Не объединяй два разных commit boundary:

- **profile commit** решает, какие данные переживут перезаход;
- **live apply** меняет текущую сцену после успешного сохранения.

## 2. Сделай versioned Reconcile идемпотентным

Используй отдельную версию миграции подсистемы, если изменение не является общей миграцией всей схемы профиля.

1. Нормализуй ownership и equipped только по существующему persistence-контракту. Не считай отсутствующую или malformed версию нулевой без основания.
2. Всегда гарантируй default-запись каждой категории и исправляй equipped ID, который отсутствует, принадлежит другой категории или не выдан игроку.
3. Только при `storedVersion < targetVersion` вычисли исторические права из авторитетного прогресса и актуального каталога.
4. Выдай ровно те записи, пороги которых уже выполнены. Не отзывай ранее выданные права без явного требования.
5. Если миграция должна впервые выбрать лучший доступный вариант, делай это только внутри version gate и детерминированно по правилу каталога.
6. Запиши новую версию после успешного backfill.
7. Повторный `Reconcile` на актуальной версии не должен снова менять equipped и перетирать ручной выбор игрока.

Версия выше известной не является причиной повторять старую миграцию. Обработай её согласно принятой в проекте forward-compatibility политике.

## 3. Проведи профильную транзакцию до live apply

До сохранения проверь, что предложенные equipped ID разрешаются в определения, а все нужные templates и live-targets валидны.

Используй последовательность:

1. Поставь защиту от повторного входа и останови затрагиваемые runtime-процессы.
2. Сними snapshot всех полей профиля и временных объектов, которые изменит операция.
3. В защищённом блоке измени профиль, вычисли награды, проверь будущий live apply и сохрани профиль.
4. При ошибке до успешного save восстанови весь snapshot, верни временные объекты, возобнови остановленные процессы и сними re-entry guard.
5. После успешного save считай профиль committed. Применяй внешний вид и остальные runtime cleanup-шаги независимо, чтобы одна ошибка не пропустила последующие шаги.
6. Ошибку post-commit live apply логируй с категорией и причиной. Не откатывай уже сохранённую прогрессию в памяти без отдельной durable compensation-транзакции.

Уведомление о награде отправляй только после commit и только если право действительно выдано впервые.

## 4. Замени template без потери live identity

### Pre-validation

До первой значимой мутации проверь весь набор категорий, который будет применён:

- существуют assets root, папка категории и нужная `Model`;
- присутствуют обязательные дети, anchors и live-root нужных классов;
- опциональные дети явно отмечены как опциональные;
- каждое копируемое свойство доступно на source и target;
- equipped ID существует, относится к правильной категории и разрешён для игрока.

Возвращай конкретный стабильный код ошибки с категорией. Не продолжай с частично проверенным набором.

### Staging

- Клонируй заменяемое содержимое до удаления старого.
- Пока возможно, держи staging вне live-иерархии.
- Вычисляй позицию через относительный transform между source-anchor и template-объектом, затем переноси его к live-anchor. Не используй абсолютные координаты template.
- До записи сохрани старые значения изменяемых свойств и список старых детей.

### Guarded commit и rollback

1. В `pcall` вставь staged-объекты и запиши подготовленные свойства.
2. При ошибке верни старые свойства и уничтожь только новые клоны или уже перемещённых staged-детей. Сам rollback выполняй best-effort и отдельно фиксируй его ошибки.
3. До необратимого шага проверь по сохранённым ссылкам, что новые объекты находятся под нужным root, а свойства получили ожидаемые значения.
4. Только после этой проверки уничтожь старые live-объекты: это commit point замены.
5. После commit проверь имена и итоговое число/наличие объектов. Ошибка здесь требует явного recovery, а не попытки восстановить уже уничтоженные Instance.
6. Всегда уничтожай временную staging-модель.

Не заменяй корневой live-Instance, если на него завязаны сервисы, connections, attributes или внешние ссылки. Для такого root меняй только содержимое: сам объект должен остаться тем же экземпляром.

Если несколько категорий применяются последовательно, заранее проверь их все. Транзакционность каждой категории не означает автоматическую атомарность всего набора; для all-or-nothing поведения нужен общий snapshot и явный rollback уже применённых категорий.

## 5. Проверь рискованные сценарии

### Каталог и migration

- каждая запись имеет уникальный стабильный ID и валидную категорию;
- для каждой категории существует ровно один default;
- legacy-профиль получает точный набор исторических прав;
- актуальная версия не запускает backfill повторно;
- повторный `Reconcile` не меняет профиль и сохраняет ручной equipped;
- malformed поля обрабатываются по текущему persistence-контракту;
- неизвестная будущая версия не запускает старую миграцию.

### Profile transaction

- ошибка asset validation происходит до save и не оставляет изменений;
- ошибка update/save восстанавливает все изменённые поля и временные объекты;
- re-entry guard и остановленные процессы восстанавливаются на каждом exit path;
- ошибка post-commit apply не отменяет committed прогрессию и не блокирует остальные cleanup-шаги;
- уведомление не дублируется для уже выданного права.

### Live template-swap

- невалидный template или live-root не меняет сцену;
- корневой Instance и его attributes остаются идентичными;
- относительный transform корректен при разных позициях template и live-anchor;
- ошибка записи свойства восстанавливает значения и удаляет staged-клоны;
- ошибка reparent не оставляет частично вставленное содержимое;
- старое содержимое удаляется только после успешного commit;
- опциональный отсутствующий объект обрабатывается явно;
- повторное применение того же варианта безопасно.

## Чеклист перед завершением

- [ ] Каталог — единственный источник соответствия stable ID, категории, template и unlock-условия.
- [ ] Historical backfill закрыт feature-local version gate и идемпотентен.
- [ ] Ручной выбор не перезаписывается после завершённой миграции.
- [ ] Profile validation и save выполняются до live apply.
- [ ] Rollback покрывает все изменённые данные и временные runtime-объекты до commit.
- [ ] Все templates проверены до первой live-мутации.
- [ ] Staging и snapshot созданы до удаления старого содержимого.
- [ ] Сохраняется identity root, а не только его имя и transform.
- [ ] Failure-path и повторный запуск закреплены автоматическими тестами.

# Runtime-эффекты апгрейдов Roblox

Превращай сохранённый уровень апгрейда в runtime-поведение на сервере. Сначала определи тип эффекта:

- **Stateful effect** меняет живой объект, например `Humanoid.WalkSpeed`, и должен повторно применяться после событий lifecycle.
- **Capacity effect** проверяется перед операцией и должен учитывать как завершённые, так и незавершённые объекты.

Не дублируй формулу уровня на клиенте или в сервисе эффекта. Читай актуальное значение через существующий серверный upgrade service или единый config.

## Сначала изучи контракт

Перед изменениями найди:

1. config и сохранённый уровень апгрейда;
2. API вычисления effect value и все пути изменения уровня, включая бесплатные grant;
3. service manifest и порядок запуска;
4. login/load, respawn, reset/Rebirth и cleanup paths;
5. владельца committed-состояния и владельца in-flight операций;
6. существующие тесты этих контрактов.

Не считай `PlayerAdded` признаком загруженного профиля. Не считай событие с названием `OnPurchased` полным источником изменений, пока не проверено, что оно также публикуется для остальных поддержанных способов выдачи уровня.

## Stateful effect

Сделай одну идемпотентную операцию `ApplyPlayer` или её проектный эквивалент. Она каждый раз читает актуальный серверный effect value, валидирует его и применяет к текущему runtime-объекту. Не кэшируй уровень в effect service.

Покрой все точки синхронизации:

- профиль успешно загружен;
- service стартовал, когда игрок и профиль уже существуют;
- персонаж появился заново после загрузки профиля;
- нужный апгрейд изменён покупкой или другим поддержанным grant;
- reset/Rebirth успешно изменил сохранённые данные.

Фильтруй события по upgrade ID. Если персонажа ещё нет, применение может быть no-op: следующий `CharacterAdded` восстановит состояние. Reset вызывает применение только после успешного изменения данных, чтобы runtime не опередил источник истины.

`Start` должен быть идемпотентным и не создавать повторные подписки. Храни Roblox connections, пользовательские disconnectors и per-player bindings; очищай их на `PlayerRemoving` и `Destroy`. В manifest запускай effect service после data/upgrade services и до сервисов, которые явно вызывают его при reset.

## Capacity effect и in-flight reservation

Проверяй эффективную занятость по инварианту:

```text
committed + reserved + requested <= capacity
```

`committed` бери из авторитетного серверного persistence/runtime state, `reserved` — у сервиса, владеющего незавершённой операцией, а `capacity` — из серверного значения апгрейда. Клиентские числа не являются источником истины. При незагруженном или некорректном committed-состоянии отклоняй новую операцию.

Для одной новой единицы допустима проверка `committed + existingReserved < capacity`, но имя параметра и комментарий должны ясно говорить, что новая единица ещё не включена в `existingReserved`. Для batch-операции передавай `requested` явно.

Выполняй check и регистрацию reservation подряд, без yield. Если между ними возможен yield или несколько исполнителей могут менять состояние параллельно, перенеси обе операции в единый `Reserve` API владельца состояния. Не удерживай reservation дольше операции.

Снимай reservation на каждом terminal path: успех, ошибка публикации, отмена, смерть, потеря базы, reset, выход игрока и `Destroy`. При успехе сначала создай committed-запись, затем сними reservation, иначе появляется окно с искусственно свободным слотом.

## Проверка

Добавь focused tests для изменённого режима.

Stateful effect:

- до загрузки профиля эффект не применяется, после загрузки — применяется;
- respawn повторно применяет актуальное значение;
- нужная покупка или grant применяет эффект, чужой upgrade ID — нет;
- reset применяет значение после изменения данных;
- уже подключённый игрок обрабатывается при старте;
- повторный `Start` не дублирует обработчики;
- `PlayerRemoving` и `Destroy` отключают все подписки;
- отсутствующий runtime-объект и невалидный effect value обрабатываются безопасно.

Capacity effect:

- последний свободный слот разрешён, следующий отклонён;
- две быстрые операции не занимают один слот;
- разные игроки не разделяют счётчики;
- отрицательные, дробные и нечисловые counts отклоняются;
- незагруженный профиль закрывает доступ;
- reservation освобождается на всех terminal paths;
- успешное завершение не создаёт промежуток между reserved и committed.

Отдельно проверь dependency order в manifest. После тестов запусти проектные formatter, linter и `git diff --check`.

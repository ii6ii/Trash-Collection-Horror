# Сокращение очереди claims после пересчёта capacity

Применяй этот паттерн, когда серверный reset меняет capacity, а часть уже принятых объектов ещё находится в пути или занимает зарезервированные слоты.

## 1. Зафиксируй контракт очереди

- Сервер определяет membership очереди, порядок claims, новую capacity и итоговый lifecycle объектов.
- При успешном принятии claim присвой ему монотонный `claimSequence`. Не выводи FIFO-порядок из обхода словаря, позиции объекта, времени прибытия или оставшейся длительности движения.
- Для равных `claimSequence` используй стабильный уникальный ID как tie-breaker.
- Перед транзакцией reset запрети новые claims владельца. Сними паузу при любом завершении операции.

## 2. Отдели чистое partition от side effects

Сделай чистую функцию с контрактом, эквивалентным:

```luau
PartitionByCapacity(claims, capacity) -> kept, released
```

Она должна:

1. Склонировать входной массив и отсортировать копию по `claimSequence`, затем по стабильному ID.
2. Нормализовать число сохраняемых записей в целое значение от `0` до количества claims.
3. Вернуть первые `capacity` записей в `kept`, остальные — в `released`.
4. Не менять исходный массив, runtime-состояние объектов и ownership.

Так partition можно проверить отдельно от Roblox Instances, движения и remotes.

## 3. Привяжи reconciliation к commit

Порядок операции:

1. Поставь приём новых claims на паузу.
2. Выполни и сохрани reset данных игрока.
3. При rollback или ошибке сними паузу без partition и без release: старые claims должны продолжить работу с прежним контрактом.
4. Только после commit вычисли capacity из нового серверного состояния и один раз раздели текущий snapshot claims.
5. Освободи overflow и обязательно сними паузу, даже если отдельный release завершился ошибкой.

Не вычисляй итоговый overflow до commit: неуспешное сохранение не должно терять или переназначать уже принятые объекты.

## 4. Освободи overflow через штатный lifecycle

Для каждой записи `released`:

- повторно найди объект по ID и проверь ownership и допустимость перехода в свободное состояние;
- возьми его актуальную позицию, а не устаревшую начальную точку движения;
- выбери ближайший валидный выход и подготовь достижимую конечную точку до очистки ownership;
- удали запись из очереди владельца, очисти owner-specific состояние и выполни штатный переход в `Free` с движением к выходу;
- увеличивай `releasedCount` только после успешного release.

Не уничтожай overflow вместо release, если этого явно не требует существующая failure policy. Если выхода нет или цель невалидна, сохрани принятую в проекте политику ошибки и закрепи её тестом; объект не должен молча остаться в противоречивом ownership/state.

## 5. Разведи уведомления по точке входа

- Для обычного UI-пути верни `releasedClaimCount` в успешном серверном ответе. Клиент выбирает уведомление о release вместо общего success, когда count больше нуля.
- Для receipt/Developer Product-пути, который не проходит через UI-контроллер, после commit разреши один серверный push об overflow.
- Не отправляй push для каждого освобождённого объекта и не дублируй его на UI-пути.
- Держи выбор канала уведомления в orchestration-слое reset, а не в чистой partition-функции.

## 6. Проверь поведение

Добавь тесты, которые доказывают:

- неупорядоченный вход сохраняет самые ранние claims и освобождает самые поздние;
- равные sequence разрешаются стабильным ID;
- capacity `0`, capacity больше длины очереди, отрицательное и дробное значение нормализуются предсказуемо;
- partition не меняет входной массив;
- после успешного reset используется новая capacity и освобождается точное число объектов;
- rollback только возобновляет очередь и ничего не освобождает;
- overflow переходит в свободное состояние и направляется к ближайшему выходу от актуальной позиции;
- `releasedClaimCount` считает только успешные release;
- UI-путь показывает release-result из ответа, receipt-driven путь получает ровно один серверный push, а отсутствие overflow сохраняет обычный success fallback;
- пауза claims снимается и после успешного завершения, и после ошибки cleanup.

После тестов запусти formatter/linter проекта и проверь diff. Не расширяй reset, persistence или систему уведомлений за пределы существующих контрактов.

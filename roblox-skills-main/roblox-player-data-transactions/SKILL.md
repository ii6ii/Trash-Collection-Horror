# Транзакции данных игрока Roblox

Строй операцию вокруг одного авторитетного изменения профиля. Предварительный snapshot нужен для UI и быстрого отказа, но не разрешает commit: между его чтением и mutation данные могли измениться.

## Сначала изучи контракт

Перед изменениями найди:

1. владельца профиля и реальные контракты `GetData`, `Update`, `Save` и проверки последнего сохранения;
2. все сервисы, которые пишут затрагиваемые поля;
3. runtime-объекты и процессы, которые операция забирает, останавливает, создаёт или уничтожает;
4. публичные error codes, analytics и существующие failure-path tests.

Не считай callback заблокированным только из-за имени `Update`. Уточни, сериализует ли API записи, допускает ли callback yield и могут ли другие исполнители менять те же данные. В однопоточном Roblox-контексте короткая функция без yield может быть атомарной относительно других задач; если такой гарантии нет, используй lock владельца данных, CAS/version marker или другой проектный механизм синхронизации.

Также установи настоящий commit point. Успешный вызов `Save` может означать durable запись, завершённый синхронный запрос или только постановку асинхронного сохранения в очередь. Не обещай durable commit, если API его не подтверждает.

## Отдели preflight от авторизации

- Читай предварительный snapshot для ответа клиенту, прогресса и дешёвого отказа.
- Не доверяй клиентским значениям Cash, стадии, цены, владения или версии состояния.
- Перед первым возможным yield проверь и установи per-player re-entry guard без промежуточного yield. Держи его до завершения save или rollback.
- Выбирай ключ guard по конфликтующему ресурсу: одного игрока достаточно только тогда, когда разные операции не могут менять тот же профиль в обход guard.
- Разные игроки не должны блокировать друг друга.

Guard предотвращает повторный запуск одной операции, но не устраняет TOCTOU между preflight и mutation. Эту гонку закрывает только повторная проверка авторитетных данных внутри атомарной mutation-секции.

## Выполни ревалидацию и mutation вместе

Внутри одного non-yielding `Update` или его проектного эквивалента:

1. заново прочитай текущие поля, от которых зависит разрешение операции;
2. заново вычисли stage, цену, лимит и остальные производные условия;
3. сравни версию или ключевые поля состояния с preflight snapshot, если операция должна применяться именно к просмотренной стадии;
4. верни стабильную доменную ошибку до первой mutation, если условие больше не выполнено;
5. сними `originalProgress` со всех полей, которые будут изменены;
6. примени все связанные изменения профиля в этой же секции.

Например, для Rebirth повторно проверь актуальные `Cash` и `RebirthCount`, затем одним изменением обнули Cash, сбрось прогресс и увеличь RebirthCount. Флаг обхода требования должен пропускать только явно разрешённую проверку, а не проверку лимита, текущей стадии или целостности профиля.

Не воспринимай `Update == true` как автоматический успех бизнес-операции: callback мог корректно отказаться без ошибки инфраструктуры. Передавай результат через отдельный локальный outcome или принятый в проекте result type.

Snapshot должен сохранять точные значения до mutation. Для таблиц делай копию, если старую таблицу будут менять in-place; одной ссылки достаточно только когда mutation заменяет поле новой таблицей и старое значение больше нигде не изменяется.

## Сохрани или согласованно откати

- По возможности выполняй до commit только обратимые runtime-действия. Необратимое удаление, выдачу награды, уведомления и аналитику оставляй после commit.
- Если до commit нужно остановить процесс или временно изъять объект, сохрани достаточно данных, чтобы восстановить тот же объект и состояние.
- При сообщённой ошибке update/save восстанови профиль через тот же защищённый mutation API, затем верни carried-объекты и возобнови остановленные процессы.
- Не позволяй rollback перезаписать более новую успешную mutation. Удерживай общий guard для всех конфликтующих writers либо проверяй transaction/version marker и ожидаемое промежуточное состояние перед восстановлением.
- Проверяй результат rollback. Его ошибку логируй отдельно от исходной причины и не скрывай частично восстановленное состояние.
- Если `Save` лишь ставит работу в очередь, немедленный успех не подтверждает durable commit и не позволяет обнаружить поздний DataStore failure. Для строгой durability используй существующее подтверждение сохранённого snapshot, journal или другой контракт проекта.

После подтверждённого commit не откатывай прогрессию из-за ошибки cleanup, визуала или analytics. Выполняй post-commit шаги независимо, чтобы сбой одного не пропустил остальные, и логируй каждый сбой с названием шага.

Строй analytics из snapshot, снятого внутри атомарной секции, а не из устаревшего Attribute или preflight-ответа.

## Заверши каждый путь

Используй защищённый блок с единым финализатором или эквивалентную структуру. Снимай re-entry guard при:

- успешном commit;
- доменном отказе после ревалидации;
- ошибке `Update` или `Save`;
- ошибке rollback или восстановления runtime;
- отмене операции и уходе игрока.

Не очищай guard раньше завершения rollback: новый запрос не должен увидеть промежуточное состояние.

## Проверка

Добавь focused tests для следующих сценариев:

- Cash или другое условие стало невалидным после preflight — mutation, save и runtime-effects не выполняются;
- stage, `RebirthCount` или version изменились после preflight — stale snapshot отклонён стабильной ошибкой;
- повторный запрос того же игрока во время save получает `InProgress` и не применяет mutation второй раз;
- операции разных игроков независимы;
- успешная операция изменяет связанные поля ровно один раз и строит analytics из атомарного snapshot;
- ошибка save восстанавливает все поля, carried-объекты и остановленные процессы;
- ошибка самого rollback видима и guard всё равно освобождается;
- ошибка post-commit cleanup не откатывает committed данные и не блокирует остальные cleanup-шаги;
- каждый ранний отказ и исключение освобождает guard.

Отдельно проверь тестом реальную семантику persistence API: синхронное подтверждение, queued save или durable snapshot. После тестов запусти проектные formatter, linter и `git diff --check`.

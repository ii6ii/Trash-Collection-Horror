# Конфликтующие ProximityPrompt

## Задача

Рядом стоят объекты, у которых действие висит на одной клавише: «положить» и «заглянуть внутрь»,
«поднять» и «толкнуть». Движок покажет оба — игрок не поймёт, какое сработает, а удержание
и короткое нажатие начнут спорить.

## Глобальную настройку не трогать

`ProximityPromptService.MaxPromptsVisible = 1` чинит один экран и ломает все остальные: там, где
рядом стоят два **не конфликтующих** объекта, один из них молча перестаёт показываться. Настройка
глобальная, а проблема локальная.

Решение — переключать `Enabled` у своих промптов по контексту.

## Один владелец поля Enabled

`Enabled` пишет **одна** сторона, и это записано в скилле системы:

| Кто владеет | Когда |
| :--- | :--- |
| Сервер | Право на действие решает сервер (разблокировано, хватает ресурса, владение объектом) |
| Клиент | Видимость зависит только от локального контекста (что в руках, открыт ли экран) |

Вторая сторона поле не трогает. Клиентская запись в поле, которое реплицирует сервер, живёт
до следующей репликации и выглядит как «промпт мигает».

## Приоритет вместо одновременности

Два промпта на одной клавише никогда не бывают `Enabled` одновременно. Правило выбора — таблица
по состоянию, а не набор независимых условий:

```lua
-- одна функция решает, что показать; ветки взаимоисключающие
if canAct(state) then          -- есть что положить/отдать
    act.Enabled, look.Enabled = true, false
elseif holdGestureActive(state) then  -- удержание занято другим действием
    act.Enabled, look.Enabled = false, false
else
    act.Enabled, look.Enabled = false, true
end
```

## Tap против hold на одной клавише

Если у объекта в руках та же клавиша занята удержанием (завязать, зарядить, разобрать), промпт
с `HoldDuration = 0` перехватит нажатие и удержание не начнётся. Промпт в этот момент **выключают
оба** — короткая ветка «ничего не показываем» обязана быть в таблице явно.

Обратное тоже верно: пока открыт экран, порождённый промптом, жест удержания глушится. Признак
открытого экрана — атрибут на игроке, который читают все, кто вешает промпты, а не локальная
переменная одного контроллера.

## Refresh после смены состояния

Промпт, выключенный по состоянию, сам не включится. Каждое событие, меняющее право на действие
(разблокировка, смена содержимого рук, конец действия, выход игрока), обязано дёргать одну функцию
пересчёта. Тихий выход из действия без пересчёта оставляет промпт выключенным навсегда — баг
воспроизводится один раз из десяти и не ищется.

Отдельно: путь `PlayerRemoving` и путь «прервано» должны пересчитывать промпты, даже когда
уведомлять уже некого.

## Поздняя привязка

Объекты появляются после старта системы (стрим, спавн, сборка уровня). Привязка промптов идёт
на `ChildAdded` папки, а не один раз в `Init`. После переподключения ремоутов промпты
перепривязываются заново — иначе живой объект остаётся без промпта.

## Дистанция

`MaxActivationDistance` у конфликтующих промптов короткий: длинная дистанция снова сводит рядом
то, что разводили по контексту.

## Чеклист

- [ ] Глобальный `MaxPromptsVisible` не трогается
- [ ] У каждого промпта записан один владелец `Enabled`
- [ ] Выбор промпта — одна функция со взаимоисключающими ветками
- [ ] Есть явная ветка «оба выключены», когда клавишу занял жест удержания
- [ ] Открытый экран помечен атрибутом, который читают все владельцы промптов
- [ ] Каждое изменение права на действие дёргает пересчёт
- [ ] Привязка на `ChildAdded`, а не однократно на старте
- [ ] `MaxActivationDistance` короткий

## Антипаттерны

- `ProximityPromptService.MaxPromptsVisible = 1` как решение
- Клиент пишет `Enabled` промпта, которым владеет сервер
- Два промпта на одной клавише включены одновременно
- Промпт с `HoldDuration = 0` рядом с удержанием на той же клавише
- Тихий выход из действия без пересчёта промптов
- `AlwaysShow` на всех промптах в зоне, где их больше одного

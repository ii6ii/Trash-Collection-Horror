## Workflow с чеклистом

Для многошаговых задач: чеклист, который Claude копирует к себе в ответ и отмечает по мере продвижения. Не даёт пропустить шаги валидации.

````markdown
## Порядок заполнения формы

Скопируй чеклист и отмечай пункты по мере выполнения:

```
Прогресс:
- [ ] Шаг 1: разобрать форму (scripts/analyze_form.py)
- [ ] Шаг 2: заполнить маппинг полей (fields.json)
- [ ] Шаг 3: проверить маппинг (scripts/validate_fields.py)
- [ ] Шаг 4: заполнить форму (scripts/fill_form.py)
- [ ] Шаг 5: проверить результат (scripts/verify_output.py)
```

**Шаг 1: разобрать форму**

Выполни: `python scripts/analyze_form.py input.pdf`

Извлекает поля формы и их координаты в `fields.json`.

**Шаг 2: заполнить маппинг**

Впиши значения полей в `fields.json`.

**Шаг 3: проверить маппинг**

Выполни: `python scripts/validate_fields.py fields.json`

Исправь все ошибки валидации перед продолжением.
````

Паттерн работает и без скриптов — для аналитических задач шаги описываются текстом.

## Цикл обратной связи

Схема «выполнить проверку → исправить ошибки → повторить» сильно поднимает качество результата. «Проверяющим» может быть скрипт или справочный документ.

```markdown
## Порядок правки документа

1. Внеси правки в `word/document.xml`
2. **Сразу проверь**: `python ooxml/scripts/validate.py unpacked_dir/`
3. Если проверка не прошла:
   - разбери сообщение об ошибке
   - исправь XML
   - запусти проверку снова
4. **Продолжай только после успешной проверки**
5. Собери обратно: `python ooxml/scripts/pack.py unpacked_dir/ output.docx`
```

Вариант без кода: «проверяющий» — STYLE_GUIDE.md, а проверка выполняется сверкой по чеклисту.

## Шаблон вывода

Жёсткий вариант, когда формат критичен:

````markdown
## Структура отчёта

ВСЕГДА используй ровно этот шаблон:

```markdown
# [Заголовок]

## Резюме
[Один абзац с ключевыми выводами]

## Находки
- Находка с подтверждающими данными

## Рекомендации
1. Конкретное действие
```
````

Мягкий вариант — тот же шаблон со словами «разумный формат по умолчанию, адаптируй под конкретный анализ».

## Примеры вход/выход

Когда качество зависит от стиля, примеры объясняют лучше описаний:

````markdown
## Формат commit-сообщений

**Пример 1**
Вход: добавлена аутентификация через JWT
Выход:
```
feat(auth): implement JWT-based authentication

Add login endpoint and token validation middleware
```

**Пример 2**
Вход: исправлен баг с некорректными датами в отчётах
Выход:
```
fix(reports): correct date formatting in timezone conversion

Use UTC timestamps consistently across report generation
```

Стиль: type(scope): краткое описание, затем подробности.
````

## Ветвление по типу задачи

```markdown
## Порядок работы с документом

1. Определи тип операции:

   **Создаётся новый документ?** → раздел «Создание»
   **Правится существующий?** → раздел «Правка»

2. Создание:
   - собрать документ через docx-js
   - выгрузить в .docx

3. Правка:
   - распаковать документ
   - править XML напрямую
   - валидировать после каждого изменения
   - запаковать обратно
```

Если ветки разрастаются, выноси каждую в отдельный файл и в SKILL.md оставляй только правило выбора файла.

## Организация по доменам

Когда справочного материала много и он разнородный, разложи его по доменам, чтобы не грузить лишнее:

```text
bigquery-skill/
├── SKILL.md              # обзор и навигация
└── reference/
    ├── finance.md        # выручка, биллинг
    ├── sales.md          # сделки, воронка
    ├── product.md        # использование API
    └── marketing.md      # кампании, атрибуция
```

```markdown
## Доступные наборы данных

**Финансы**: выручка, ARR, биллинг → [reference/finance.md](reference/finance.md)
**Продажи**: сделки, воронка → [reference/sales.md](reference/sales.md)
**Продукт**: использование API → [reference/product.md](reference/product.md)
```

На вопрос про выручку Claude прочитает только `finance.md`; остальные файлы не стоят ни одного токена, пока не понадобились.

## Скилл со скриптами

Готовый скрипт лучше сгенерированного на лету: он надёжнее, не тратит токены на генерацию и даёт одинаковый результат при каждом запуске.

Правила для скриптов в скиллах:

- **Решай, а не перекладывай.** Скрипт обрабатывает ошибочные ситуации сам (нет файла — создать с дефолтом, нет прав — вернуть пустое значение с понятным сообщением), а не падает в расчёте на то, что Claude разберётся.
- **Никаких «магических» констант.** `TIMEOUT = 47` без объяснения — плохо. Каждое значение сопровождается комментарием, почему именно оно: если ты не знаешь правильного значения, Claude тем более не выведет.
- **Подробные сообщения об ошибках** валидаторов: «Поле 'signature_date' не найдено. Доступные поля: customer_name, order_total, signature_date_signed».
- **Документируй интерфейс** каждого скрипта в SKILL.md: команда запуска и формат вывода.
- **Явно указывай зависимости**: «Установи: `pip install pypdf`», а не «используй библиотеку для PDF».
- **Проверяемые промежуточные результаты** для пакетных и разрушительных операций: схема «разобрать → создать файл плана → проверить план скриптом → применить → проверить результат». Ошибки ловятся до внесения изменений, а план можно переделывать, не трогая оригиналы.

## MCP-инструменты в скиллах

Всегда указывай полное имя инструмента `ServerName:tool_name` — без префикса сервера Claude может не найти инструмент, особенно когда подключено несколько MCP-серверов.

```markdown
Используй инструмент BigQuery:bigquery_schema для получения схемы таблиц.
```

## Антипаттерны

| Антипаттерн | Вместо этого |
| :--- | :--- |
| Объяснять то, что модель знает («PDF — это формат файлов…») | Сразу давать специфичный для проекта контекст |
| Перечислять пять библиотек на выбор | Один дефолт + аварийный выход для особого случая |
| Обратные слеши в путях (`scripts\helper.py`) | Прямые слеши везде, включая Windows |
| Ссылки в глубину: SKILL.md → advanced.md → details.md | Все ссылки на один уровень от SKILL.md |
| Даты и «сейчас/скоро» в тексте | Раздел «старые паттерны» для устаревшего |
| Смесь синонимов: поле / бокс / элемент / контрол | Один термин на понятие по всему скиллу |
| Общие имена: `helper`, `utils`, `tools` | Имя, по которому понятно, что делает скилл |
| `context: fork` на наборе гайдлайнов без задачи | Форк только для скиллов с явной задачей |

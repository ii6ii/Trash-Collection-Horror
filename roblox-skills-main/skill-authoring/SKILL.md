# Создание скиллов

## Когда нужен скилл

| Задача | Решение |
| :--- | :--- |
| Повторяющаяся процедура, чеклист, многошаговый workflow | **Скилл** |
| Постоянный факт о проекте (структура, команды сборки) | CLAUDE.md |
| Поведение нужно гарантировать детерминированно | hook |
| Нужна изоляция контекста под большую задачу | сабагент или скилл с `context: fork` |

Признак того, что пора делать скилл: одни и те же инструкции вставляются в чат вручную, или раздел CLAUDE.md разросся из факта в процедуру. Тело скилла грузится только при использовании — длинный справочник в скилле почти ничего не стоит, пока не понадобился, в отличие от CLAUDE.md.

## Куда класть

| Уровень | Путь | Область |
| :--- | :--- | :--- |
| Личный | `~/.claude/skills/<имя>/SKILL.md` | все проекты пользователя |
| Проектный | `.claude/skills/<имя>/SKILL.md` | только этот проект |
| Плагин | `<plugin>/skills/<имя>/SKILL.md` | где включён плагин |

При совпадении имён личный перекрывает проектный. Скилл любого уровня перекрывает bundled-скилл с тем же именем (но не его алиасы). Плагинные живут в namespace `plugin:skill` и не конфликтуют.

**Имя команды берётся из имени каталога**, а не из поля `name` — для личных и проектных скиллов `name` это только подпись в списке. Каталог `deploy-staging/` даёт `/deploy-staging`.

Claude Code следит за каталогами скиллов: правки `SKILL.md` подхватываются в текущей сессии без рестарта. Рестарт нужен, только если каталога скиллов не существовало на старте сессии.

## Минимальный скилл

```yaml
---
description: Что делает скилл и когда его применять.
---

Инструкции, которым Claude следует при запуске скилла.
```

Все поля frontmatter опциональны; практически обязателен только `description` — без него Claude не поймёт, когда применять скилл (в этом случае берётся первый абзац тела). Frontmatter читается, только если открывающий `---` — первая строка файла.

Полная таблица полей: [reference/frontmatter.md](reference/frontmatter.md).

## Имя скилла

- Только строчные латинские буквы, цифры и дефисы, до 64 символов.
- Нельзя зарезервированные слова `anthropic` и `claude` в имени.
- Хорошо: герундий или предметная фраза — `processing-pdfs`, `pdf-processing`, `deploy-staging`.
- Плохо: `helper`, `utils`, `tools`, `data`, `files` — по имени непонятно, что делает.

## description — самое важное поле

Именно по нему Claude выбирает скилл из сотни доступных. В нём должно быть **что скилл делает** и **когда его применять**.

- Пиши в третьем лице: «Извлекает текст из PDF…», а не «Я помогу тебе…» и не «Ты можешь…». Описание попадает в системный промпт, смешение лиц ломает выбор скилла.
- Включай слова-триггеры, которые реально произносит пользователь.
- Ключевой сценарий — первым: `description` вместе с `when_to_use` обрезается на 1536 символах в листинге скиллов.
- Лимит поля — 1024 символа, без XML-тегов.

Хорошо:

```yaml
description: Извлекает текст и таблицы из PDF, заполняет формы, объединяет документы. Использовать при работе с PDF-файлами или когда пользователь упоминает PDF, формы или извлечение из документов.
```

Плохо: `Помогает с документами`, `Обрабатывает данные`, `Делает всякое с файлами`.

## Тело скилла

Содержимое скилла попадает в разговор одним сообщением и **остаётся в контексте на последующих ходах**. Claude не перечитывает файл — пиши то, что должно действовать всю задачу, как постоянные инструкции, а не как одноразовые шаги.

- Каждая строка — повторяющаяся стоимость в токенах. Не объясняй то, что модель и так знает: не нужно рассказывать, что такое PDF или зачем нужен git.
- Держи `SKILL.md` меньше 500 строк. Всё, что больше, — в отдельные файлы.
- Один термин на одно понятие по всему скиллу («поле», а не вперемешку «поле/бокс/элемент/контрол»).
- Не пиши то, что протухнет («до августа 2026 используем старый API»). Устаревшее выноси в раздел «старые паттерны».
- Не предлагай пять вариантов — дай один дефолт и, если нужно, аварийный выход: «Используй pdfplumber. Для сканов с OCR — pdf2image + pytesseract».
- Пути только через прямой слеш: `scripts/helper.py`, не `scripts\helper.py`.

## Progressive disclosure

```text
my-skill/
├── SKILL.md          # обзор и навигация (обязателен)
├── reference/
│   ├── api.md        # читается по необходимости
│   └── examples.md
└── scripts/
    └── helper.py     # выполняется, не читается в контекст
```

Ссылки на вспомогательные файлы держи **на один уровень от SKILL.md**. Вложенные цепочки (SKILL.md → advanced.md → details.md) читаются частично — Claude превьюит их вместо полного чтения и теряет информацию.

В reference-файлы длиннее 100 строк добавляй оглавление в начале.

Явно указывай намерение для скриптов: «Запусти `scripts/analyze.py`» (выполнить) против «Смотри `scripts/analyze.py` — там алгоритм разбора» (прочитать).

## Степень свободы

Точность инструкций подбирается по хрупкости задачи:

- **Высокая свобода** — текстовые указания. Когда валидны несколько подходов и решение зависит от контекста (код-ревью).
- **Средняя** — псевдокод или скрипт с параметрами. Когда есть предпочтительный паттерн, но вариации допустимы.
- **Низкая** — конкретная команда без вариантов: «Выполни ровно `python scripts/migrate.py --verify --backup`. Не меняй команду и не добавляй флаги». Когда операция хрупкая и порядок критичен (миграции БД).

## Кто вызывает скилл

| Frontmatter | Вызывает пользователь | Вызывает Claude |
| :--- | :--- | :--- |
| по умолчанию | да | да |
| `disable-model-invocation: true` | да | нет (описание не грузится в контекст) |
| `user-invocable: false` | нет | да |

`disable-model-invocation: true` — для всего с побочными эффектами: `/commit`, `/deploy`, отправка сообщений. Claude не должен решать задеплоить, потому что код «выглядит готовым».

`user-invocable: false` — для фоновых знаний, которые не являются действием (`legacy-system-context`).

## Инструменты и запуск в сабагенте

`allowed-tools` разрешает инструменты без запроса подтверждения **на тот ход, в котором вызван скилл** — грант снимается со следующим сообщением пользователя. Ограничением он не является: остальные инструменты остаются доступны по обычным правилам permissions.

`disallowed-tools` наоборот убирает инструменты из пула на время действия скилла.

`context: fork` запускает скилл в изолированном сабагенте: тело скилла становится промптом, история разговора недоступна. Поле `agent` выбирает тип (`Explore`, `Plan`, `general-purpose` или свой из `.claude/agents/`). По умолчанию форк уходит в фон; `background: false` заставляет дождаться результата в том же ходу. Форк имеет смысл только для скиллов с явной задачей — набор гайдлайнов без задачи вернётся ни с чем.

## Динамический контекст и аргументы

Скилл может подставить в промпт вывод shell-команд и аргументы вызова. Синтаксис, подстановки (`ARGUMENTS`, `CLAUDE_SKILL_DIR`, `CLAUDE_PROJECT_DIR`) и подводные камни: [reference/substitutions.md](reference/substitutions.md).

Главное про Windows: инъекция команд идёт через Bash или PowerShell. `shell: bash` на Windows без Git Bash валит вызов скилла целиком. В этом проекте Git Bash есть, но если скилл пишет PowerShell-команды — ставь `shell: powershell`.

## Проверка

Срабатывание и качество проверяются отдельно:

1. Собери 3–5 реальных формулировок запроса, на которых скилл должен срабатывать, и пару, на которых не должен.
2. Прогони каждую **в свежей сессии** — контекст, оставшийся от написания скилла, маскирует дыры в инструкциях.
3. Сравни с прогоном без скилла (отключить можно через `skillOverrides` в `.claude/settings.local.json`).
4. Не срабатывает — усиливай `description` ключевыми словами. Срабатывает лишний раз — сужай `description` или ставь `disable-model-invocation: true`.

Если frontmatter не парсится, скилл грузится с пустыми метаданными: `/имя` работает, автосрабатывание — нет. Проверка синтаксиса: `claude plugin validate .claude/skills`.

## Чеклист перед коммитом

- [ ] `description` в третьем лице, содержит и «что делает», и «когда применять», с триггерными словами
- [ ] Имя каталога = команда, которую хочется набирать
- [ ] Тело меньше 500 строк, без объяснений очевидного
- [ ] Ссылки на вспомогательные файлы — на один уровень
- [ ] Термины единообразны, дат и «сейчас/скоро» нет
- [ ] Пути через прямой слеш
- [ ] Побочные эффекты закрыты `disable-model-invocation: true`
- [ ] Проверено в свежей сессии на реальных запросах

## Добавление скилла в этот проект

`.claude/skills/` здесь подключён как git-сабмодуль (`gitlab.com/roblox-dvlprs/roblox-skills`), поэтому коммитов всегда два:

```bash
cd .claude/skills
git add <имя-скилла> && git commit -m "..." && git push

cd ../..
git add .claude/skills && git commit -m "Update skills submodule: ..."
```

Забыть второй коммит — значит оставить в основном репозитории указатель на старую версию, и у коллег скилла не будет.

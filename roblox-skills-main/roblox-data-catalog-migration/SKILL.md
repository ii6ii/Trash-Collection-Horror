# Миграция data-driven каталога Roblox

Применяй этот workflow, когда меняется состав или порядок каталога, а его ID связаны с ассетами или сохранениями.

## 1. Установи контракт данных

1. Прочитай исходную таблицу/ТЗ, каталог, его типы, lookup-таблицы, все call sites и связанные тесты.
2. Найди поля, которые хранятся в DataStore/ProfileStore, передаются по remotes или записаны в Studio-ассетах.
3. Классифицируй ключи:
   - **стабильный ID** — идентичность записи, ассета или сохранённого объекта;
   - **rank/tier** — изменяемый балансный порядок;
   - **внешний ID** — доменная метка из ТЗ, которая не обязана совпадать с одним из первых двух.
4. Если назначение ключа не доказано кодом, сохранениями или иерархией Studio, не переназначай его по позиции в массиве.

## 2. Составь карту перехода

До правок составь для каждой старой записи карту:

```text
старый rank | новый rank | стабильный ID | действие: keep/move/retire | влияние на persistence
```

- При пересортировке меняй rank, но не стабильный ID.
- Путь, имя модели или другая ассетная ссылка должны строиться из стабильного ID, если именно он задаёт Studio-ассет.
- Источником прогрессии должен быть rank/tier, а не ID или имя ассета.
- Не вводи алиас вроде `level` для `rank` автоматически. Сохрани его только если реальные call sites или публичный контракт ещё от него зависят.

## 3. Обнови каталог и потребителей

- Создай отдельные lookup-таблицы по стабильному ID и rank/tier. Ключи должны быть уникальными, а rank/tier — непрерывным, если этого требует прогрессия.
- Сверь каждую строку каталога с исходной таблицей. Не заменяй точную сверку проверкой вроде `value > 0`.
- Найди все производные значения: урон, HP, income, награды, боссы, offline-расчёты, кэши и лимиты прогрессии. Обнови только реальные зависимости.
- Если значение дублируется в другом конфиге, либо выводи его из каталога, либо закрепи тестом равенство двух источников.
- Не убирай связь каталога с Rebirth, unlock или другой механикой только потому, что она мешает новому максимуму. Для этого нужно явное требование.

## 4. Мигрируй persistence поэтапно

1. Сохрани исходную `SchemaVersion` **до** `Reconcile` или другого заполнения default-значений.
2. Оформи каждую миграцию отдельным version gate: `if previousVersion < targetVersion then ... end`.
3. Старые version gates не сворачивай в один вайп: профиль может пропустить несколько версий и должен пройти все нужные этапы.
4. Для retired-записей используй явное множество ID. Числовой диапазон допустим, только если карта перехода доказывает, что весь диапазон и только он устарел.
5. По умолчанию сохраняй активные ID, данные вне явной области миграции, malformed-записи и несвязанные части профиля, если задача не требует их чистить.
6. Политику для отсутствующей или malformed `SchemaVersion` бери из текущего persistence-контракта; не приравнивай её к нулю без основания.
7. Запиши новую `SchemaVersion` только после успешного выполнения всех этапов.
8. Не запускай миграцию на production-данных и не публикуй place без явного разрешения.

## 5. Проверь изменение

Добавь или обнови тесты, которые доказывают:

- построчное совпадение каталога с исходной таблицей;
- уникальность стабильных ID, внешних ID и rank/tier;
- связь ассета со стабильным ID, а не с его новой позицией;
- корректную границу максимального rank/tier и равенство производных значений каталогу;
- прохождение профиля через несколько пропущенных `SchemaVersion`;
- удаление только retired ID и сохранение активных, внедиапазонных, malformed и несвязанных данных;
- идемпотентность: повторная загрузка уже мигрированного профиля не меняет его снова.

После тестов запусти проектные formatter/linter и проверь diff. Не оставляй измененные ожидания в тестах без объясняющего изменения production-кода или исходных данных.

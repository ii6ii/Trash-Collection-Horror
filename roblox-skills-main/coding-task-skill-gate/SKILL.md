# Skill-gate для кодовых задач от часа

## Правило

Кодовая задача с оценкой **≥ 1 час** (не вёрстка GUI и не дизайн-графика) перед мержем обязана
назвать **один из четырёх исходов** — в описании MR или комментарием в задаче:

| Исход | Когда |
| :--- | :--- |
| **Обновить существующий скилл** | Дефолт. Тема уже покрыта — дополнить, а не заводить второй |
| **Новый скилл** | Только если ни один существующий скилл тему не покрывает |
| **Заметка в репозитории игры** | Знание привязано к архитектуре одной игры |
| **Письменный отказ** | Причина из списка ниже |

Ни одного из четырёх — блокер ревью (категория 9).

**Ссылка на skill-MR сама по себе гейт не закрывает.** Ревьюер открывает diff и проверяет
содержание. Скилл, не прошедший приёмку, — тот же блокер, с формулировкой «скилл не проходит
приёмку», а не «скилла нет».

## Тест переносимости — главный критерий

Вычеркнуть из скилла все имена модулей, сервисов, римоутов, конфигов и все числа этой игры.
Осталось хотя бы одно применимое утверждение — скилл проходит. Не осталось ничего — это конспект
тикета, ему место в репозитории игры.

## Что принимать

- скилл применим в репозитории, где нет ни одного упомянутого в нём файла;
- `description` собран из слов, которые произносит человек с задачей; номер тикета — только хвостом
  (`История: ABC-123.`), не как триггер;
- есть хотя бы одна ловушка или «почему так» — то, что не вычитывается из кода: расхождение
  с документацией Roblox, порядок инициализации, поведение API, что сломалось в проде;
- имена файлов и числа — помеченный пример, не содержание: их нет в чеклисте и в антипаттернах;
- в заголовке нет названия игры.

## Что отклонять

- перечень модулей, которые добавил MR, и список имён римоутов;
- числа геймдизайна (вместимость, таймеры, цены, лимиты) как содержание скилла;
- дубль существующего скилла под другим именем;
- «как я это сделал» без утверждения, применимого в другой игре.

## Валидные причины отказа

- применён существующий скилл без изменений — назвать какой;
- задача целиком про контент, числа или ассеты одной игры;
- одноразовая миграция или разовый фикс данных;
- баг-фикс, где причина — опечатка или локальная логика, без переиспользуемого принципа;
- знание записано в репозитории игры — дать ссылку.

Не отказ: «некогда», «и так понятно», «тривиально» без причины из списка.

## Дедупликация

Перед заведением **нового** скилла — пройтись по каталогам `.claude/skills/` по двум-трём ключевым
словам темы. Пересечение — обновлять существующий. Два скилла на одну тему — блокер.

## Сабмодуль

В каждом игровом репозитории:

```text
.claude/skills  →  https://gitlab.com/roblox-dvlprs/roblox-skills
```

```bash
git submodule add https://gitlab.com/roblox-dvlprs/roblox-skills.git .claude/skills
git submodule update --init --recursive
```

Сабмодуль общий для всех игр — поэтому в нём живёт только то, что проходит тест переносимости.
Специфика игры идёт в её собственный репозиторий: заметку — в `docs/`, эвристики ревью —
в `.claude/review-heuristics.md` (этот файл читает скилл ревью MR).

## Workflow после фичи

1. Проверить дедупликацию: есть ли уже скилл на эту тему.
2. Написать или дополнить `.claude/skills/<kebab-name>/SKILL.md` (см. `/skill-authoring`).
3. В сабмодуле: ветка → commit → push → MR в `roblox-skills`.
4. В игровом репозитории обновить указатель сабмодуля после мержа skill-MR.
5. В MR игры вставить ссылку на skill-MR, ссылку на заметку **или** текст отказа.

Забыть шаг 4 — значит оставить указатель на старую версию, и у коллег скилла не будет.

## Антипаттерны

- Закрывать гейт скиллом, написанным «чтобы был», вместо обновления существующего
- Ревьюер аппрувит по факту ссылки, не открыв diff скилла
- Специфика одной игры уезжает в общий сабмодуль, потому что больше некуда
- Номер тикета как основной триггер в `description` — в новой игре такой триггер мёртв
